# Задание - <<Не мигрируй с Си на Раст, попивая сок у себя в квартале>>

Так вышло, что вы -- разработчик в компании <<Тилламук>>. Это маленькая компания на пять тысяч человек, занимающаяся разработкой IaaS- и SaaS-решений в основном на языках Си и Rust. Вы работаете в команде поддержки внутреннего инструментария. Вам уже известно, что для разработки этого инструментария компания использует собственный [DSL](https://en.wikipedia.org/wiki/Domain-specific_language) (domain-specific language). Учитывая специфику высшего руководства, за основу этого `DSL` был взят [изотерический язык](https://en.wikipedia.org/wiki/Brainfuck) (далее `BF`).

Этот `DSL` -- интерпретируемое расширение языка `BF`, называемое `BFPP` (`BF++`). Его спецификация находится в файле [language_specs.md](language_specs.md). Сам интерпретатор написан на языке Си ещё прежней командой разработки, которая, к сожалению, больше недоступна из-за географических ограничений.

Перед вами стоит следующая задача: перенести этот интерпретатор на Rust, поскольку все разработчики вашей команды работают на этом языке.

## Исходная кодовая база (что вы увидели, когда открыли проект)

В проекте имеется кодовая база среднего размера на языке Си. Разработчики писали этот код под впечатлением от C++, поэтому его архитектура построена с использованием структур, хранящих собственные виртуальные таблицы вызовов. Это упрощает проектирование, но усложняет поддержку такого кода.

От прошлых разработчиков, как вы уже заметили, сохранились изображения архитектуры при её проектировании (`diagrams`).

В проекте также есть система сборки и интеграционные тесты. Запустить те тесты, которые есть можно через `make test`.

## Pull request с решением на Rust

Отправьте решение отдельным PR. В корне репозитория должны находиться `Cargo.toml` и закоммиченный `Cargo.lock`. Проект может быть Cargo workspace, но должен предоставлять бинарную цель с именем `bfpp`, собираемую командой `cargo +stable build --locked --release --bin bfpp` из корня репозитория. Внутреннюю архитектуру спроектируйте средствами Rust; интерфейс CLI и поведение языка сохраните совместимыми с исходной реализацией.

Интеграционные тесты уже находятся в репозитории. Они запускают бинарник отдельным процессом и не зависят от устройства вашей библиотеки:

- `tests/run_bfpp_tests.py` выполняет 51 программу из `tests/cases/`, подаёт байты из `INPUT` на stdin и точно сравнивает stdout с `OUTPUT`. Ненулевой код завершения или таймаут считаются ошибкой.
- `tests/test_cli.py` выполняет 15 сценариев из `tests/fixtures/cli/cases.json`: аргументы, BF и BF++, обе ленты, бинарный ввод-вывод и ошибки. Проверяются код завершения, stdout и заданные фрагменты stderr; для успешных сценариев stderr должен быть пустым.

Сохраните эти тесты и фикстуры в PR. CLI принимает `bfpp [--dialect=bf|bfpp] [--tape=fixed|grow] <file>`; значения по умолчанию — `bfpp` и `grow`. Коды завершения: `0` — успех, `1` — ошибка чтения, компиляции или выполнения (включая неизвестный диалект или тип ленты), `2` — неверная форма команды. Ожидаемые фрагменты диагностик указаны в `tests/fixtures/cli/cases.json`.

Локально перед отправкой PR те же проверки:

```sh
rustup toolchain install stable --profile minimal --component rustfmt --component clippy
cargo +stable fmt --all --check
cargo +stable check --locked --workspace --all-targets --all-features
cargo +stable clippy --locked --workspace --all-targets --all-features -- -D warnings
cargo +stable test --locked --workspace --all-features
cargo +stable build --locked --release --bin bfpp
python3 -B -m unittest discover -s tests -p test_bfpp_runner.py
python3 -B tests/run_bfpp_tests.py -- ./target/release/bfpp
python3 -B tests/test_cli.py ./target/release/bfpp
```

## Оценка

### Обязательные пункты

- Решение на Rust, проходящее все тесты из репозитория.
- Использование идиоматичного Rust и возможностей языка, изученных в курсе. Если вам кажется, что подходящих мест для использования тех или иных средств Rust нет, специально искать их не нужно.
- Адекватное качество кода: понятные имена переменных, отсутствие мёртвого кода и неиспользуемых переменных. Кодовая база должна проходить проверки с помощью `cargo fmt`, `cargo check` и `cargo clippy`.
- Документация по использованию разработанного инструмента.

### Что **только** повышает балл

- Проект может быть реализован не только как готовый инструмент, но и как библиотека, пригодная для интеграции в другие проекты. Например, такая библиотека позволит выполнять программы на `BFPP` из кода другого приложения.
- Механика стека вызовов функций в `BFPP` может быть неидеальной, особенно с учётом возможной будущей реализации отладчика. В идеале данные о функциях должны храниться отдельно, чтобы к ним можно было удобно получать доступ.

### Что **только** понижает балл

- Наличие неоправданных предупреждений о качестве кода.
